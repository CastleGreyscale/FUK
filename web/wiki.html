Overview

FUK (Framework for Unified Kreation) is a local-first AI rendering pipeline built for VFX professionals. It provides a structured, stable environment for image and video generation that integrates cleanly into existing production pipelines — without telemetry, cloud dependencies, or workflows designed around consumer use cases.

FUK runs entirely on your hardware. Models, outputs, and project data stay on your machine.

Design Philosophy

Most AI generation tools are built around exploration — infinite scroll, quick iterations, no project structure. FUK is built around production. Every output lives in a project/shot/version hierarchy. Every generation captures complete metadata. Nothing is ephemeral unless you want it to be.

The pipeline is intentionally minimal in its interface and maximal in its output. Controls are exposed where they matter. Defaults are sane. The goal is repeatability and composability with downstream tools, not hiding complexity behind a friendly UI.

What FUK Is Not

  • Not a cloud service — no API keys, no usage limits, no data leaving your machine
  • Not a consumer tool — designed for pipeline integration, not social sharing
  • Not a model trainer — FUK generates; training happens in dedicated tools
  • Not locked to one model family — new pipelines can be added via configuration

FUK is in active development. Core generation is stable. AOV outputs are functional but being refined. See the roadmap section on the main page for current focus areas.

Prerequisites

  • Python 3.10+
  • CUDA 11.8+ (NVIDIA) or compatible AMD drivers
  • Git
  • FFmpeg

Steps

  1. Clone the repository:
    git clone https://github.com/CastleGreyscale/FUK
  2. Install dependencies:
    pip install -e .
  3. Run setup:
    chmod +x setup.sh && ./setup.sh
  4. Configure models — edit config/models.json to select which models to use, remove entries for any you don't want
  5. Set model root — edit config/defaults.json and set the model root directory to wherever your models live
  6. Download models:
    ./download_models.sh
  7. Launch FUK:
    ./start.sh

If Model Downloads Are Slow

Models come from one of two hosts. DiffSynth defaults to ModelScope, which is often slow and prone to dropped connections outside China. Most models are also on HuggingFace, which is usually far faster:

DIFFSYNTH_DOWNLOAD_SOURCE=huggingface ./download_models.sh

A few repositories exist only on ModelScope — the PAI/* models and DiffSynth-Studio's converted Wan safetensors. The downloader falls back per component, so either choice completes; those specific files just come over the slower link.

Downloading by hand. If the terminal download crawls along at under 1MB/s or keeps failing, fetching the files through a web browser is a perfectly good alternative and is often dramatically faster. The only requirement is that files land where FUK expects them:

<models_root>/<model_id>/<pattern>

So models_t5_umt5-xxl-enc-bf16.safetensors from DiffSynth-Studio/Wan-Series-Converted-Safetensors belongs at:

<models_root>/DiffSynth-Studio/Wan-Series-Converted-Safetensors/models_t5_umt5-xxl-enc-bf16.safetensors

Watch for subdirectories. The Wan A14B models keep their weights in high_noise_model/ and low_noise_model/, each split across several shards — recreate those folders rather than flattening everything into one directory.

Re-run ./download_models.sh afterwards to check your work. Files already in the right place are detected and skipped, so a run that downloads nothing means the layout is correct.

First Launch

On first launch FUK will verify model paths and report any missing files. The server runs at http://localhost:8000 by default (easily changed if needed). If a model fails to load it will appear grayed out in the model selector — check the terminal output for the specific error.

See the GitHub README for the complete and up-to-date installation instructions, including Windows/WSL2 setup.

VRAM Considerations

VRAM requirements scale with model size and output resolution. As a rough guide:

  • 8GB — base image generation at moderate resolutions; some models will not load
  • 12GB — comfortable for most image generation pipelines
  • 16GB+ — video generation, high-resolution image gen, AOV passes
  • 24GB — full pipeline with all features; recommended for production use

FUK will attempt to offload to system RAM when VRAM is insufficient, but generation will be significantly slower. The VRAM Management preset in each generation panel controls the offload strategy.

Disk Space

  • Base install: ~15GB
  • Models: 50GB–500GB+ depending on selection — see File Locations for where models are expected
  • Outputs: variable; EXR files with all AOV passes are substantially larger than standard image formats

Model and application install directories can be on separate drives. See the Windows Storage Doc for model location considerations on Windows.

Detail Bias

The sampler runs a denoising schedule from high noise (sigma ≈ 1.0, where global composition is decided) down to clean (sigma ≈ 0, where fine texture and edges form). At Detail Bias 1.0 the full schedule runs. Below 1.0, the high-noise front is truncated and the same step count is repacked into a smaller, lower-noise window — so a larger share of compute lands in the texture-forming band.

The result is grittier surfaces, more visible micro-detail, and slightly less of the "diffusion smoothness" sheen. Composition becomes more conservative (the model has less room to wander globally), which makes this knob pair naturally with reference images and ControlNet conditioning where you didn't want global drift anyway.

The slider is clamped to 0.85–1.00; values below 0.85 strip too much of the composition phase and produce broken output. Try 0.85–0.90 for noticeable grit, 0.95 for a subtle bump.

The three video families disagree on nearly every hard limit, so the sampling controls are model-driven rather than fixed. Each model declares a constraints block — the family block lives in defaults.json, and any model may override individual keys in models.json. Sizes and frame counts always round up onto the grid, matching what the pipelines enforce internally — a request never silently yields a smaller or shorter clip than asked. Rounding happens before conditioning media is loaded, so the first frame, keyframes and control video land on the same canvas the model actually runs at, and the generation history records the effective values rather than the requested ones. At 24fps the ~5-second point is 121 frames for Wan and LTX-2, 124 for MiniMax-H3.

Controls that a model has no use for are hidden rather than left inert: LTX-2 and MiniMax-H3 both drop DiT Switch Boundary, Sliding Window and TeaCache, and MiniMax-H3 additionally drops the LoRA stack, which its pipeline does not support. Values for a hidden control are not posted either, so the generation history never records a setting the model did not apply.

Output Format

Video is saved as a PNG frame sequence plus a composited MP4 for preview. The frame sequence is the primary output — import it directly into Nuke, After Effects, DaVinci Resolve, or any compositing application. EXR passes are generated per-frame when AOV export is enabled via the Layers Panel.

Frame rate can be increased post-generation via FILM interpolation. See Frame Interpolation. Interpolation runs on the frame sequence, not the MP4.

Regional Conditioning (EliGen)

▶ Video breakdown — coming soon

EliGen integration brings regional conditioning directly into the generation pipeline. Define compositional zones within the frame and assign independent parameters to each — separate prompts, weights, and conditioning per region. This gives you direct spatial control over composition without relying entirely on prompt engineering.

How It Works

Rather than sending a single prompt to the model and hoping for a specific composition, EliGen lets you explicitly partition the frame. Each zone is a mask that defines a spatial area, paired with a prompt and weight that apply only within that area. Zones are composited during the denoising process — the model integrates them into a coherent result rather than pasting regions together.

EliGen is activated by selecting a Qwen Image + EliGen model in the Image Panel. Zone masks are loaded as .psd or .ora files — each layer in the file becomes a separate conditioning zone.

Practical Notes

  • The global prompt still applies to the whole frame — zone prompts add to it rather than replace it
  • Zones work best for broad compositional control (foreground subject, background environment, sky) rather than fine detail placement
  • EliGen and ControlNet can be used together — ControlNet handles structural conditioning, EliGen handles content per region
  • Create zone masks in any application that exports layered PSD or ORA files — Photoshop, Krita, and Affinity Photo all work

Post-Processors

▶ Video breakdown — coming soon

Two finishing passes — upscaling (raise resolution) and frame interpolation (raise frame rate). Both run in the Postprocess Panel, take the same input types (image, video, or frame sequence), and save their result as a new version alongside the original. Neither requires re-running generation.

Work in progress. The post-processors are the least mature part of FUK. Both are constrained by what is available under an open-source licence that also permits commercial use — the current models are older, image-only, and have no temporal awareness. Better options exist, but they are either closed, research-only, or non-commercial, and are not shipped here.

In practice results fall short of the dedicated tools in Topaz, Resolve, Nuke, or Twixtor. Use these passes for previews, dailies, and quick turnarounds; for final delivery, take the frame sequence out to a purpose-built tool. New models are added as licensing allows.

SeedVR2 — the temporal option

Status: under evaluation. SeedVR2 is wired up, measured and usable, but it has not yet been signed off as part of the finishing pipeline. The open question is whether the detail it invents is acceptable on clean generated footage — see the two caveats below before committing a shot to it. It is deliberately kept out of the latent → EXR path for the reasons under Bit depth.

SeedVR2 restores a clip as a sequence rather than as a stack of unrelated frames, so detail stays put instead of crawling. It is the default for video and the only upscaler here worth calling a finishing step. Weights download with download_models.sh, or automatically on first use, into {models_root}/seedvr2.

A caveat worth setting expectations on. SeedVR2 is a restoration model — it was trained to recover detail from degraded footage. Pointed at already-clean output it has little real detail to recover, so it invents some, and what it invents varies between frames. Measured on a clean 640×360 clip, frame-to-frame correlation dropped from 0.65 in the source to about 0.25 after restoration, with a period-4 component appearing that matches the VAE's 4× temporal compression. In practice that reads as motion stepping or fine detail shimmering. The 7B model and a wider frame window both reduce it; neither eliminates it. It pays off most on genuinely soft or compressed source.

Motion blur, stepping and ghosting

The most common complaint about SeedVR2 output — that fast-moving subjects look like they are stepping, with detail ghosting between frames — has one cause, and it is not a bug. SeedVR2 removes motion blur, because that is what a restoration model does. Measured on a Wan clip, the fast-moving region of frame came back roughly 10× sharper (variance of Laplacian 19–28 in the source, 185–266 restored), consistently on every frame.

Motion blur is what makes 24fps read as smooth motion. Strip it out and each frame becomes a crisp snapshot at a distinct position, so the same displacement now reads as stepping — and because the restored detail is hallucinated independently per frame, its shape shifts slightly between frames, which reads as ghosting.

Motion Protection is the fix. It blends each pixel back toward the source in proportion to how fast that pixel is moving, so moving subjects keep their blur while still areas keep the full sharpening. Measured on the same clip at the default 0.7:

RegionSeedVR2 sharpening retained
Fast-moving hand19% — keeps its motion blur
Subject / chair37%
Still background78% — keeps the sharpening

The mask comes from the source, not the restored frames, since the source is what still carries honest motion blur. A static shot produces a near-zero mask and passes through untouched, so there is no reason to turn this off unless you specifically want the full de-blurred look. It costs a few seconds per clip.

Bit depth, and why SeedVR2 is not in the EXR path

SeedVR2 is 8-bit display-referred at both ends. This is not a setting — it is fixed in the engine:

  • Input is divided by 255 on load, so a 16-bit PNG is misread rather than merely truncated
  • Internals run at fp16
  • Output is multiplied by 255 and cast to uint8, on every write path

There is no float path, no linear-light path, and no way to carry values above 1.0 through it. Patching the engine would take only a few lines, but it would not help: the model was trained on display-referred video, so linear HDR is out of distribution for it. SeedVR2 belongs in display space — that is where it is correct, not a limitation to route around.

This matters because the latent → EXR path does real work that 8-bit throws away. It decodes the latent in float32 rather than bf16, optionally decodes several times with scale or noise bracketing and fuses them with Mertens exposure fusion to recover range a single decode cannot give, then converts sRGB → linear. All of that happens at decode, before any quantisation. Put SeedVR2 downstream of it and the result is crushed to 8-bit immediately — you would be writing float32 EXR containers holding round-tripped 8-bit sRGB, with the bracketing entirely wasted.

Note also that there is no latent-space option: SeedVR2 carries its own VAE and cannot consume Wan latents. The latent must be decoded to pixels first, whatever route you take.

Four ways to sit the two together, in rough order of preference:

ApproachTrade-off
Keep SeedVR2 out of the EXR path (current behaviour)EXR stays the clean linear master at native resolution; SeedVR2 serves delivery and preview. Loses nothing.
Clean resample — lanczos-upscale the float32 linear decodeLarger EXR, full range preserved, nothing invented. Often preferable for VFX: hallucinated detail is not real information and will not match across shots or against plates.
Detail transfer — composite SeedVR2's detail as a ratioUpscale the HDR cleanly, run SeedVR2 on a tonemapped copy, then multiply the HDR by enhanced / unenhanced. Transfers detail without replacing pixels, so highlights above 1.0 survive. Standard practice for folding an LDR-only enhancement into a linear pipeline. Costs real complexity, and the ratio needs guarding in near-black.
Patch the engine for float I/ONot recommended. A few lines, but you would carry a patch on a vendored repo and still have the out-of-distribution problem.

The general principle: the EXR is the master and should stay clean, linear and full-range. AI enhancement is a look decision, and look decisions are better applied downstream where they can be judged and reverted than baked into the master.

Real-ESRGAN Has No Temporal Model

Real-ESRGAN has no temporal model. Applied to video it enhances each frame in isolation, and because it hallucinates detail independently per frame, that detail crawls and shimmers between frames. On Wan output — where frame-to-frame motion is already slightly irregular — this is very visible. Use SeedVR2 for video and keep Real-ESRGAN for stills.

Frame Interpolation

FILM (Frame Interpolation for Large Motion) synthesizes intermediate frames to increase the effective frame rate of generated video. Useful for smoothing motion, converting a 12fps generation to a 24fps deliverable, or creating slow-motion sequences from standard-rate output.

How FILM Works

FILM uses a learned model to estimate motion between adjacent frames and synthesize intermediate frames that are temporally consistent. Unlike traditional optical flow methods, it handles large displacements and occlusions more gracefully — making it a better fit for AI-generated content where frame-to-frame motion can be irregular. It is the best-performing interpolator currently available to FUK under a licence that is both open source and commercially usable.

Parameters

ParameterDescription
Source FramerateThe frame rate of the input sequence — must match the actual rate the sequence was generated at
Target FramerateDesired output frame rate — FILM synthesizes however many intermediate frames are needed to reach it
Video Output ModeWhether to produce an MP4 preview alongside the output frame sequence

Bit depth, and the EXR route

FILM sits differently from SeedVR2 here, and the distinction is worth understanding.

The 8-bit limit is FUK's, not the model's. FILM is a plain PyTorch module in our own code and its interpolation call takes arbitrary float tensors. Everything restricting it to 8-bit lives in our wrapper: frames are loaded with cv2.IMREAD_COLOR (which forces 8-bit) and divided by 255, and saved clamped to [0,1] as uint8. On CUDA it also runs at fp16, not float32. A 16-bit save path exists but is currently unused, and clamps to [0,1] regardless. Raising this to float32 linear would therefore be a change to two methods, not a patch against a vendored repo — the open question is behavioural rather than structural, since FILM was trained on display-referred images. It should tolerate linear light better than a restoration model would, because interpolation is mostly geometric — estimate motion, warp, blend — but this is untested.

Bit depth is the smaller problem, though. Interpolation changes the frame count, and in a VFX sequence the beauty EXR has to stay in lockstep with its AOVs:

  • Cryptomattes cannot be interpolated at all. They are object ID maps — a blend of two IDs is not a third object, it is a meaningless value
  • Depth blends across occlusion edges, producing surfaces that never existed
  • Normals need renormalising after any blend, and interpolated normals drift off the unit sphere

The fix is ordering, not precision. Interpolate the beauty first, then generate depth, normals and crypto from the interpolated sequence. Every layer then derives from the same frames, and crypto is regenerated by SAM2 on real images rather than blended. Interpolating after AOV generation desynchronises the sequence and silently corrupts the mattes — silently being the dangerous part, since a corrupted crypto matte still looks like a crypto matte.

There is no latent-space shortcut either, for a different reason than SeedVR2's: Wan's VAE is 4× temporally compressed, so latent frames are not video frames and interpolating them would interpolate groups of four.

Practical Notes

  • FILM performs best with smooth, continuous motion — highly chaotic or flickering content will not interpolate cleanly
  • Generated at 12fps → interpolated to 24fps is the most common workflow
  • Interpolation does not generate new content — it synthesizes in-between frames; it cannot recover motion that wasn't present in the original generation
  • Interpolation runs on the frame sequence, not the MP4 preview — load the sequence directory, not the video file

FUK generates Arbitrary Output Variables (AOVs) alongside the beauty render via the Layers Panel. These technical passes enable compositing, grading, and integration with professional DCC tools downstream.

Work in progress. AOV outputs are being refined and quality is improving across builds, but set expectations accordingly: the passes here are estimated from a finished image by inference models, not rendered from scene geometry. The constraint is as much licensing as it is quality. What is left is usable for comp work but is not on par with the equivalent tools in Nuke, Houdini, or a production renderer. Where a pass is critical, treat FUK's output as a starting point to be cleaned up rather than a finished deliverable.

3D Reconstruction

▶ Video breakdown — coming soon

Generates proxy 3D geometry from images — either captured photos or Qwen-generated orbital views from the LoRA Dataset Builder. The tool lives in the Utilities tab, alongside the Spec Tool and Dataset Builder.

The target output is production-useful proxy geometry: collision meshes, depth references, NeRF initialization, and geometry-informed passes for compositing. Synthetic-to-3D — driving reconstruction from generated views rather than photographs — is the workflow this exists for.

This is not photogrammetry. Qwen is a generative model, not a physically consistent renderer, so geometry across generated views is approximate by construction. For prop reference, collision meshes and compositing depth guides this is fine. For precision measurement or hero asset creation it is not.

Two Model Tiers

ModelInputOutputVRAMSpeed
TRELLISSingle imageTextured GLB mesh with baked UVs~12GB peak~55s typical
VGGT1 to hundreds of imagesGLB mesh + PLY point cloud + camera solve~13GB peak~10s inference

TRELLIS decodes Structured 3D Latents into a mesh and bakes a texture onto it. VGGT is a single feed-forward transformer that returns camera parameters, dense depth and a 3D point cloud in one pass — no pairwise matching, no global bundle adjustment. Choose TRELLIS for a fast proxy from one image; choose VGGT when you have coverage.

Image Count Guidance (VGGT)

Angular spread matters more than raw count — clustered views give diminishing returns. The panel warns live as you add or remove views.

ViewsResult
4–6Rough proxy, usable for quick geometry reference
8–12Solid object reconstruction — recommended minimum for a clean mesh
16–24Full 360° coverage with top and bottom; best results

Input Selection

Three input sources: a multi-select file browser, a folder (expanded recursively), or the Dataset Builder shortcut, which lists every generated dataset and loads its approved or generated views in one click.

Selected views appear in a vertical filmstrip between the settings and the viewport. Click any thumbnail to toggle it in or out of the solve — excluded views grey out but stay visible, so the angular spread of the full set stays readable while you narrow it down. All / None / Invert act on the whole set. Drag the splitter to trade filmstrip width against viewport size; double-click it to reset.

This matters more than it sounds. Finding a working image set is mostly elimination — bad angles, inconsistent subject scale, and views the generator rendered differently all drag the reconstruction down, and pulling them out is far quicker than re-picking the input from scratch.

Background Handling

VGGT reconstructs a scene, not an object — it assigns depth to every pixel, background included. A plain studio backdrop is textureless, so those depths are unconstrained and the model invents a curved sheet behind the subject. Across generated views those invented sheets disagree with each other, and the point cloud ends up with a shell of contradictory geometry wrapped around the subject. On a 64-view test orbit, 69% of surviving points were backdrop.

Matting your source images to alpha does not fix this on its own: VGGT composites transparency onto white before inference, which produces exactly the white background that causes the problem. FUK applies alpha after inference instead, where it works.

ModeBehaviour
Remove studio backdrop (default)Keys out bright, near-neutral pixels before meshing. A brightness slider handles pale subjects being over-cut.
Use source alpha matteUses the input images' alpha channel; falls back to backdrop keying when there is none.
Keep everythingCorrect for environment and scene captures, where the background is the subject.

Viewer

A Three.js viewport with matcap shading — deliberately minimal, since this is a proxy review tool rather than a material editor. Left-drag orbits, scroll zooms, right-drag pans. Reframe recentres on the geometry. Toggle between Solid, Wireframe and Point Cloud; when a run exports more than one format, switch which file the viewport is showing. Meshes carrying a baked texture (TRELLIS) render with it rather than matcap. Download buttons are provided per exported format.

Installation Note

VGGT runs in FUK's main environment and needs no extra setup. TRELLIS requires CUDA extensions that conflict with FUK's PyTorch build, so it installs into its own isolated environment and runs as a subprocess — this keeps image and video generation safe from its dependencies. Run bash fuk/core/threed/install_trellis_env.sh once to build it. Until then TRELLIS shows as unavailable in the model list, with the missing pieces named; VGGT is unaffected.

Storyboard Tab

The Storyboard tab is FUK's project-level pre-production surface. It sits above the per-shot files rather than replacing them: each panel corresponds to one shot, the imagery and action drafts authored here get pushed into that shot's Image or Video tab, and the per-shot JSON remains the source of truth for generation settings, history, and pinned versions.

Everything on this tab autosaves on a short debounce — there are no Save buttons. The manifest lives next to your shot files as {projectname}_storyboard.json.

Layout

Two stacked sections:

  • Globals — project-wide settings that apply across every shot: project tags, mood, default seeds, active LoRAs.
  • Shots — a grid of panel cards, one per shot, plus an Add Panel card at the end.

A snapshot bar sits above both, providing dated copies of the manifest and one-click restore.

Project Tags

Reusable #markers scoped to this storyboard. Each tag has a name (becomes #name), a category (character, prop, location, other), and a value — the text that #name expands to at generation time. Type # in any storyboard or shot prompt to autocomplete against them.

Project tags shadow workspace tags on marker collision, so a project-local #sarah can override a global #sarah without touching the global tag library. Values themselves can contain other #markers — useful for layering a character description on top of a costume tag.

Mood / Setting

A single sentence merging style and environment (e.g. neo-noir, low-key lighting, rain-soaked Tokyo back alleys at night). It is appended to every shot's prompt at generation time as Mood: …, so a project-wide tone change is one edit rather than a per-shot sweep. This is the "storyboard-level prompt injection" referenced in the Prompt Panel.

Default Seeds

Optional uint32 seeds for image and video. They are baked into a new shot's seed slot the first time you Send the panel to that tab; the shot's seed then lives independently in the Image/Video Seed Control. Changing the global later does not retroactively touch shots that have already received a send. Leave blank to let each shot stay on random.

Each seed field offers Random (generate a new value) and Clear (drop back to random-per-shot) controls.

Active LoRAs

A project-wide toggle list of every LoRA discovered in your install, grouped by model family. Activating a LoRA does two things:

  • Surfaces its trigger_word as a #marker in # autocomplete across every prompt field in the project.
  • Adds any caption phrases the LoRA shipped with to the same autocomplete feed.

It does not automatically attach the LoRA to a shot's generation — the Image/Video tab's LoRA selection still controls what actually loads. Active LoRAs are an authoring affordance: they let you reference the right trigger without flipping back to model docs.

Panel Card

One card per shot. The header shows the shot ID and a save pip. The body has two columns:

  • Imagery (still) — describes the frame: composition, lighting, lens, mood, subject. Pushed to the shot's Image tab positive_prompt.
  • Action (motion) — describes motion within the shot: camera move, subject action, beat timing. Pushed to the shot's Video tab positive_prompt.
  • Duration (s) — planned shot length, for downstream edit handoff.
  • Notes — freeform director notes; storyboard-only.

Both prompt fields accept #markers from project tags, workspace tags, and active LoRAs — markers stay raw in the manifest and resolve live at generation time, so editing a tag value updates every shot that references it.

Side-by-side previews show the current image and video pinned to this panel. Drag any item from Generation History onto a preview slot to pin it — the drop also mirrors the originating prompt into the matching panel field (image → imagery, video → action). The × on a preview clears it.

Send to Image / Send to Video

Each panel has a "→ Image" and "→ Video" button with an adjacent model select. The button flushes any unsaved draft, writes the raw markered prompt into the shot file's positive_prompt, and (if the model select is set) also writes that model selection into the shot. You stay on the Storyboard tab — the Image/Video tab will reflect the change the next time you visit it. If the affected shot happens to be the one currently loaded, its in-memory state is refreshed so you don't see a stale prompt on the next visit.

The model select is per-panel and persists in the manifest. Leave it on (tab default) to keep whatever model the destination tab already had.

Send buttons are disabled when the corresponding prompt field is empty, or when the shot file does not yet exist (the card shows a no shot file warning in that case — create the shot first via Add Panel).

Add Panel

Creates a new panel and the matching shot file in one click. The shot ID must start with an alphanumeric character and may contain letters, digits, and hyphens (up to 32 chars). The new shot file appears in the Project Bar immediately.

Snapshots

The snapshot bar at the top saves a dated copy of the current manifest, lists existing snapshots in a dropdown, and restores any of them with confirmation. Snapshots are the storyboard's version-up mechanic — useful before a structural re-cut or a destructive Mood/Active-LoRA change.

The storyboard does not sync bidirectionally with shot files. Send is one-way (storyboard → shot). If you edit the prompt in the Image or Video tab after sending, re-sending will overwrite that edit — version up the shot first if you want to preserve it.

VRAM Management

▶ Video breakdown — coming soon

The VRAM Management dropdown lives in the Generation card of both the Image and Video tabs (and in the Postprocess Panel). It selects the offload strategy FUK uses to fit a model into available GPU memory. The trade-off is always the same: the more of the model that is offloaded to system RAM or disk, the lower the VRAM floor and the slower the generation.

Presets

PresetStrategyVRAM RequiredSpeed Impact
NoneNo offloading — full model in VRAM48GB+Fastest
LowCPU offload in bfloat1616–24GBMinimal
MediumCPU offload in float812–16GBModerate
HighDisk offload8GBSignificant — requires a fast SSD

How to Choose

  • Start at the lowest offload level your card can hold and only move up if you hit out-of-memory errors.
  • Larger output resolutions — and, for video, longer frame counts — raise the VRAM ceiling, so a preset that works for a short clip may need bumping up for a longer one.
  • High (disk offload) is a last resort for 8GB cards; it leans on SSD read speed and is dramatically slower than the CPU-offload presets.

The dropdown overrides the launch default for the current session only — it does not persist to disk. The persistent default and advanced knobs like buffer_gb (activation headroom; raise it if you OOM mid-generation) and computation_dtype live in defaults_vram.json.

Deleting weights

Models can be removed from disk from the same row. Deletion is share-aware, and that matters more than it sounds: the Qwen-Image VAE backs eight models and the Wan T5 encoder five, so removing a model naively would take shared components with it and break most of the registry. A component used by any other entry is never deleted, and the panel names the models keeping it.

It is a two-step action. The first click asks for a plan — what goes, what is kept and why, how much is reclaimed — and removes nothing. Only confirming that plan deletes anything, and nothing is recoverable except by re-downloading. Any pipeline currently loaded for the model is evicted first, so weights never vanish underneath a live pipeline.

Prompt Panel

▶ Video breakdown — coming soon

The Prompt Panel is the floating control in every Image and Video tab where you author the positive and negative prompt. It is more than a textarea: it unifies your saved prompt tags, the trigger words of installed LoRAs, and caption analyses exported from the LoRA builder into a single shorthand vocabulary. From that vocabulary you have three ways to build a prompt — fast inline shorthand, structured slot picks, or an LLM refinement — and they all share the same source of truth.

The Three Modes

  • Inline shorthand (# autocomplete) — type # in the prompt textarea and a dropdown of matching tokens appears above the field. Selecting one inserts a marker (e.g. #noir) at the caret. Markers stay in the text as you write — they're expanded later on Compile or Expand.
  • Slot picker — toggle Slots in the header to open a category grid of available tokens. Drilling into a category lists every token in it; clicking one drops it into the Style chip tray below the prompt rather than into the textarea inline. This keeps subject/action language in the main field and accumulates style intent separately so Compile can produce a disciplined two-paragraph prompt.
  • LLM refine (Expand) — sends your current draft plus style chips plus the same vocabulary to qwen3-vl:8b and asks it to refine the text into a cinematographer-grade prompt. The model is instructed to use vocabulary phrases verbatim and preserve your existing intent rather than rewrite from scratch.

The Vocabulary

Every dropdown and slot list draws from one combined token list. Source badges identify where each came from:

  • tag — your saved entries from the Describe & Tag tool. Edit them at fuk/ui/data/prompt_tags.json or via the Describe & Tag UI.
  • lora — synthesized from fuk/config/defaults_loras.json. Each entry's trigger_word becomes a marker, and its inject_text becomes the expansion. The list is filtered by the current model's family (a Qwen tab won't see Wan-only LoRAs).
  • phrase — top bigrams and trigrams imported from caption analyses dropped in fuk/ui/data/lora_captions/ by the standalone LoRA builder. These only appear when the matching LoRA is active in the model panel. They have no marker — they insert as raw text since they're already short natural-language phrases.

Compile (Deterministic)

Compile expands every #marker in the textarea against the vocabulary, then appends a trailing Style: … sentence built from the chip tray. The result is written back to the textarea and the chip tray clears. No LLM is involved.

  • If the textarea already ends in . ! or ? the punctuation isn't doubled.
  • A blank line separates the main paragraph from the Style: sentence so the textarea reads as two paragraphs.
  • Unknown markers (no matching tag or LoRA) stay in place and surface as a warning under the textarea.
  • If an active LoRA's trigger word never appears in the prompt, the response includes missing_lora_triggers — the UI doesn't auto-inject anything, but it's there so a future check could surface it.

Expand (LLM)

Expand runs the same Compile step internally to produce a concrete draft, then sends that draft along with the vocabulary list to qwen3-vl:8b. The system prompt instructs the model to:

  • Refine the draft rather than rewrite it
  • Use vocabulary phrases verbatim where they apply
  • Preserve the Style: sentence as authoritative
  • Add motion language for Video tabs; suppress it for Image tabs
  • Return JSON: { positive, negative, notes? }

On success the textarea is replaced with the model's positive prompt, the negative prompt is updated only if the model provided one, the chip tray clears, and any notes appear as a dismissible note under the warning row. Requires Ollama running and qwen3-vl:8b pulled — see Describe & Tag for setup. Every request uses keep_alive: 0 so the LLM is evicted from VRAM immediately and the generation pipeline gets it back.

Style Chips

The chip tray appears below the prompt textarea whenever slot picks accumulate. Each chip shows the token's display name; hover for its expansion. Click the × on a chip to remove it, or clear on the tray header to drop them all. Chips persist visually until Compile or Expand bakes them into the textarea — at which point the tray clears.

Chips don't persist across shot switches in v1; they live only in panel state. For project-wide style injection (apply a sentence to every shot in a sequence), use the Mood field on the Storyboard tab — it appends to every shot's prompt at generation time.

Disabling States

  • Compile is enabled when the prompt contains at least one #marker or there is at least one style chip.
  • Expand is enabled when the prompt has any non-empty text or at least one style chip.
  • Both buttons are disabled while a generation is running on the host tab.

Tag Marker Format

Markers are lowercased, slug-safe versions of the token name: spaces become _, and only letters/digits/underscore/hyphen are allowed in the body. A tag named Low Key becomes #low_key. LoRA markers come straight from each entry's trigger_word field, so however you spell the trigger in defaults_loras.json is the marker you type.

Marker collisions resolve in this order, first match wins: tags, then LoRA triggers. That means a user-authored tag of the same name overrides the auto-generated LoRA shorthand — useful when you want to swap a LoRA's default inject_text for your own phrasing without touching the LoRA config.

API Endpoints

  • GET /api/prompt/tokens?model=…&active_loras=… — unified token feed: tags + family-filtered LoRA triggers + caption phrases (only for active LoRAs). Returns { tokens, categories, model_family, active_lora_triggers }.
  • POST /api/prompt/compile — deterministic expansion. Body { text, model?, active_loras?, style_chips?, style_label? }, returns { compiled, expanded_markers, unknown_markers, missing_lora_triggers, style_sentence }.
  • POST /api/prompt/expand — LLM refinement. Body { text, model?, active_loras?, style_chips?, mode, intent? }, returns { positive, negative, notes?, model, mode }.

Describe & Tag

The Describe & Tag tool lives in the Utilities tab. It is the first slice of FUK's LLM integration: a vision-language model (Ollama-hosted) writes a cinematographer-style description of any image or short video clip, and lets you save fragments of that description as named prompt-shorthand tags for reuse later in the pipeline.

Requirements

  • Ollama running locally (default http://localhost:11434). FUK does not spawn or manage it — start ollama serve separately
  • The configured vision model pulled: ollama pull qwen3-vl:8b (≈6 GB on disk, ≈6–7 GB VRAM at runtime)
  • The health indicator at the top of the tool reports green when both conditions are met

Override the model with FUK_LLM_MODEL and the host with OLLAMA_HOST environment variables. Every request uses keep_alive: 0 so the LLM is evicted from VRAM immediately after each call, leaving room for the generation pipeline.

Describe an Image

  1. Click the drop zone to open a native file dialog and pick any image
  2. Click Describe Image — the image is downscaled to 1024px JPEG and sent to the model
  3. The result lands in an editable textarea so you can refine wording before tagging

Describe a Video

The same tool handles short video clips. Selecting a video file (.mp4 .mov .webm .mkv .avi .m4v) switches the preview to a playable video and the run button to Describe Video.

  • The response includes the number of frames used, and the timeout extends to 120 s for the multi-frame call

Metadata Format

Sidecar files are standard JSON, saved as meta.json in the version directory. They are human-readable and can be parsed by any standard JSON library. No database or index is required — the History panel reads sidecar files directly from disk.

Metadata Display

The Generation History gallery renders a generation's captured metadata as a structured settings panel rather than a raw JSON dump. Curated fields — resolution, seed, steps, CFG, denoise, sigma shift, exponential shift μ, frame count, sliding window, model, and the LoRA stack — are surfaced as compact labelled cells in a consistent order, while long or path-like values such as LoRA names and source paths get their own full-width rows for readability. Any parameter not in the curated list still appears automatically via a generic pass, so newly added generation settings show up in the panel without a UI change. Positive and negative prompts render as their own text blocks, and two generations can be opened side by side for a field-by-field A/B comparison of their settings.

Portability

Because metadata is stored as sidecar files alongside outputs rather than in a central database, output directories are fully portable. Copy a version directory to another machine and FUK will recognize it on first launch. If a model file referenced in the sidecar is missing or has a different hash, FUK will warn before re-queuing.

What "Non-Commercial" Means Here

For DSINE and VGGT the restriction attaches to what you use the tool for, not to whether you redistribute FUK. Never packaging or selling FUK does not exempt you. If you are paid for work whose pipeline included either, that is commercial use under the plain reading of these licences.

DSINE is the most explicit — its clause 2(b)(4) prohibits "use of the Software to provide any service to an external organisation for which payment is received." That is precisely the freelance and studio-work case.

Commercial paths exist: DSINE via researchcontracts.engineering@imperial.ac.uk, and VGGT via Meta.

FLUX Is a Special Case

FLUX's licence is not a flat prohibition, and it is easy to read either way. Two clauses pull in opposite directions.

Outputs are explicitly permitted: "We claim no ownership rights in and to the Outputs… You may use Output for any purpose (including for commercial purposes)." Outputs are not Derivatives; the only restriction is that you may not train a competing model on them.

Model use is not: "You may only access, use, Distribute, or create Derivatives of the FLUX.1 [dev] Model… for Non-Commercial Purposes" — and Black Forest Labs define Non-Commercial Purpose to exclude "revenue-generating activity."

So selling an image you generated is squarely permitted; running the model as part of paid work is the contested act. BFL's own tier structure settles how they read it — their Professional tier is sold to agencies producing work "on behalf of named clients," and the entry Builder tier is explicitly "not meant for client use or downstream applications."

Practical reading: personal work, R&D and unpaid experiments are fine on FLUX.2-dev. Paid client deliverables want a Builder or Professional licence, or a different model.

FLUX.1 Krea [dev] is the BFL × Krea collaboration finetune and carries the same non-commercial terms. Despite the name it is not a friendlier option, and it is not the same thing as Krea 2 below.

Krea 2 — The Permissive Alternative

Krea's own from-scratch 13B model, unrelated to the FLUX collaboration, ships under the Krea 2 Community License:

  • Commercial use is free below $1,000,000 USD company-wide annual revenue (trailing twelve months, all affiliated entities). Above that, an enterprise licence is required.
  • You own your outputs — Krea claims no ownership.
  • Two conditions apply at every size: implement reasonable content filtering (an open-source classifier, a moderation API, or human review all qualify), and disclose AI generation where legally or platform-required.
  • Ships as Raw (undistilled, for fine-tuning and LoRA training) and Turbo (8-step distilled). Gated on Hugging Face — accept the licence and Acceptable Use Policy to download.

For a freelancer or small studio this is currently the most permissive frontier-class image model, and a better default than FLUX.2-dev for anything client-facing.

Blender Bridge

▶ Video breakdown — coming soon

The Blender Bridge is a Blender add-on (fuk/plugins/blender/) that drives FUK from inside Blender. It renders your scene's structural control passes, sends them to FUK for control-guided generation, and returns the result to the viewport — for both stills and VACE-driven video. It targets Blender 4.2+ and is validated on 5.x.

Requires a running FUK server on the same machine, plus the relevant model weights: qwen_image_control_union_2512 (or qwen_image_control_union) for stills, and wan_vace_a14b for video.

Installation

  1. Start the FUK server.
  2. In Blender: Edit ▸ Preferences ▸ Add-ons ▸ Install from Disk… and pick fuk/plugins/blender/addons/fuk_blender.zip. Enable FUK Bridge.
  3. Set the Server URL in the add-on preferences if it isn't the default (http://localhost:8000).
  4. Open the FUK tab in the 3D viewport sidebar (press N).

Connecting to a Shot

Pick your project folder (the one holding the shot .json files) and press Connect; the button reads Connected once it reaches the server. The add-on also auto-connects on file open when a project folder is saved in the .blend, and restores the last shot you used.

Load Shot mirrors the shot's prompt, seed, and settings into the panel (the shot is the source of truth); Save to Shot writes your edits back. Advanced settings you don't edit in Blender — LoRAs, detail bias, VRAM preset — are read from the shot at generation time, so changes made in the FUK web UI apply automatically.

Control Passes

The bridge derives structural control from your 3D scene, which is far more accurate than estimating it from a 2D render:

  • Depth — the exact Z pass, normalized (near = white, far = black, background masked) to match the convention the control model expects.
  • Normals — the normal pass, remapped.
  • OpenPose — from a view layer that renders your pose rig; falls back to FUK's estimator if no rig layer is set.
  • Canny — derived by FUK from the beauty render.

Generating Stills

Frame your camera, choose a control, and press Quick Preview (fast, low-res) or Render Full. The add-on renders the beauty and control passes, sends them to the control-union model, and returns the image. History policy: Quick Preview is ephemeral, Render Full saves a complete entry (result + control + source), and Save to History promotes any result on demand. The FUK web history auto-refreshes when Blender saves.

Prompts support FUK's #tags: Insert #tag searches the vocabulary and Preview shows the resolved prompt.

Result Display

Under Result, choose how the image comes back: Viewport (a camera-background overlay with adjustable opacity, registered to your framing), New Window, or Image Editor. With Diffusion Preview on, the image is shown forming step-by-step during generation.

Live Mode

Toggle Live for an IPR-style loop: after you move the camera or edit geometry and the scene settles for the Delay, it auto-runs a Quick Preview. With Interrupt on, a new edit cancels the in-flight preview and restarts with the latest state; with it off, edits made mid-render coalesce into a single trailing render. Selection clicks are ignored. Shortcuts (3D View): Ctrl+Shift+P preview, Ctrl+Shift+L toggle Live.

Video (Wan-VACE)

Animate a still with your scene's motion:

  1. Generate a still first — it becomes the VACE reference (the look).
  2. Set the scene frame range (the motion) and a depth / normals / openpose control.
  3. Set Video % (resolution scale) and press Generate Video.

The add-on renders the control pass over the whole range into a folder (depth is normalized over a global range so it doesn't flicker) and runs wan_vace_a14b with that sequence as the control video and your still as the reference. The result loads into Blender's Video Sequencer. Video is slow and runs on demand — there is no live mode for it.

Cancelling

Press Esc or the Cancel button to stop a generation. Image generations abort at the next diffusion step; video currently stops waiting but continues rendering on the server.
